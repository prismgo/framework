# 工作原则

## 开始任务

- 明确目标、影响范围和验证方式；存在会改变实现方向的不确定性时先说明并询问。
- 优先选择能完整满足需求的最小方案，不增加未要求的抽象、配置或扩展点。
- 只修改与任务直接相关的文件和代码；保持相邻代码风格，不顺手重构无关内容。
- 先验证问题或失败边界，再实现；修复后用同一入口复验。

## 变更边界

- 未经明确授权，不改变公共 API，不保留兼容代码，不新增第三方依赖。
- 不忽略错误：能返回时返回，否则使用 `exception.Report(...)`；该 API 不可用时记录日志。
- 发现无关死代码、孤立代码或兼容回退时先报告，不擅自删除或扩大任务范围。
- 不提交密钥、本地凭据、覆盖率产物或临时运行数据。

## 沟通

- 使用与用户一致的语言，结论和进度保持简洁。
- 需要澄清时一次只问一个问题，并给出可直接选择的具体方案。
- 只声称实际执行过的验证；未完成项和风险必须明确说明。
