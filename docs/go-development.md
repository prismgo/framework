# Go 开发规范

## 编码

- 遵循标准 Go 约定：`gofmt`、Tab 缩进、短包名、导出符号 `PascalCase`、内部符号 `camelCase`。
- 优先复用现有实现和标准库；只有现有边界不适用时才做局部重构。
- 函数、类型、接口、文件和包保持单一职责，逻辑显式，命名与相邻组件一致。
- 导出符号使用英文文档注释；复杂实现和设计原因可用中文注释。注释解释原因和约束，不复述代码。
- 新建或修改的非平凡函数、类型及复杂测试逻辑必须补充有用注释。

## 错误与公共行为

- 优先向调用方返回错误；只有 Facade 解析或启动期不可恢复的错误可以 panic。
- 不静默吞错，不用默认值掩盖必需服务或配置缺失。
- 公共 API 变更、第三方依赖或兼容层必须先获得用户批准。

## 测试

- 行为变更应添加或更新同包 `*_test.go`；跨组件行为使用集成测试。
- 测试文件和用例名沿用邻近风格，如 `service_provider_test.go`、`redis_lifecycle_test.go`。
- 测试辅助函数调用 `t.Helper()`，资源清理使用 `t.Cleanup()`。
- 先判断失败来自错误的测试装配还是真实生产缺陷。缺失必需依赖导致的测试 panic 属于测试问题。

## 禁止的测试修复

未经明确批准，不得为不完整测试而在生产代码中：

- 增加测试专用分支、Helper 或替代运行路径；
- 把必需服务改为可选，或以静默默认值替代解析失败；
- 仅为避免测试 panic 增加无业务依据的 nil 检查；
- 弱化验证、生命周期或 Provider 要求。

只有有效运行配置能够证明真实生产缺陷时，才修改生产代码。

## 代码索引

新增包、文件或导出符号时更新 `CODE_INDEX.md`，保持“元信息 → Quick Lookup → 包详情 → 约定”的结构；表格应列明关键符号或源码文件，不使用含糊的“等”。
